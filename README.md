# كريبتو البلحوسي

يتكوّن المشروع من تطبيق Android للمستخدمين، وتطبيق Android منفصل للمدير في
`manager_app/`، وواجهة Supabase Edge Function وقاعدة PostgreSQL. خدمة
FastAPI في `server/` بديل للاستضافة الذاتية وليست المسار المختار هنا. لا نعتمد
لوحة ويب للإدارة. النظام معلوماتي فقط: لا ينفّذ صفقات ولا يطلب مفاتيح تداول.

## وضع المشروع

- تطبيق المستخدمين يسجل الدخول ويتحقق من التجربة المجانية ذات الأيام الخمسة
  ويجلب الإشارات المحمية من واجهة Supabase. واجهة PHP القديمة لا تدعم
  تسجيل الدخول أو الاشتراكات، لذلك لم تعد صالحة كمصدر للتطبيق.
- تطبيق المدير المستقل يعرض المستخدمين والإشارات، ويمدد الاشتراك شهراً بعد
  تأكيد العملية، ويضبط الحد الأدنى للتوافق ومنصات البيانات. يتحقق الخادم من دور
  المدير لكل مسار إداري.
- التطبيقان يستخدمان رابط الدالة المنشورة عبر HTTPS كمتغير GitHub Actions
  `API_BASE_URL`، ومفتاح Supabase العام `SUPABASE_ANON_KEY`. اترك
  `MANAGER_API_BASE_URL` غير مضبوط عادةً كي يستخدم تطبيق المدير الرابط نفسه.
- خادم FastAPI يقرأ بيانات السوق العامة من Binance Futures وBybit وOKX؛ ملفات
  PHP القديمة لا تحتوي هذا الماسح ولا تنشئ إشارات تلقائياً.
- انظر [تهيئة Supabase والنشر](#تهيئة-supabase-والنشر) للمسار المعتمد دون
  بطاقة دفع، أو [تعليمات FastAPI](./server/README.md) للاستضافة الذاتية.

## تهيئة Supabase والنشر

1. استخدم مشروع Supabase جديداً وفارغاً أو تأكد أن الجداول الواردة في الترحيل
   غير موجودة. لا تشغّل SQL يدوياً؛ سير العمل يطبّق الترحيل ويسجل إصداره.
2. في مستودع GitHub افتح **Settings → Secrets and variables → Actions**. أضف
   المتغيرين التاليين:
   - `API_BASE_URL`: `https://<project-ref>.supabase.co/functions/v1/api/`
     (استبدل `<project-ref>` بالجزء السابق لـ `.supabase.co` في Project URL).
   - `SUPABASE_ANON_KEY`: مفتاح `anon`/`publishable` العام الظاهر في إعدادات
     API في Supabase. هذا المفتاح مخصص للاستخدام العام داخل التطبيق؛ لا تضع
     مفتاح `service_role` هنا.
3. أضف GitHub Actions **Secrets** المطلوبة لسير العمل
   `.github/workflows/deploy-supabase.yml`:
   `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`,
   `JWT_SECRET`, `ADMIN_EMAILS`, `SCAN_SECRET`, `BREVO_API_KEY`, و`SMTP_FROM`.
   أنشئ `JWT_SECRET` و`SCAN_SECRET` عشوائيين مستقلين، بطول 32 بايت على الأقل،
   ولا ترسلهما في المحادثة. قيمة `ADMIN_EMAILS` هي بريد المدير الذي سيسجل
   الحساب به. يجب أن يكون مرسل Brevo موثقاً؛ البريد مطلوب كي يتمكن المستخدمون
   من تأكيد حساباتهم.
4. شغّل يدوياً GitHub Actions workflow المسمى **Deploy Supabase API**. سيطبّق
   ترحيل قاعدة البيانات، ويحفظ أسرار الدالة في Supabase، وينشر `api` مع تعطيل
   تحقق JWT الافتراضي في البوابة؛ الدالة نفسها تتحقق من رموز الدخول الخاصة بها.
5. بعد نجاح النشر، اتبع
   [`supabase/SCAN_SCHEDULING.md`](./supabase/SCAN_SCHEDULING.md) لتمكين
   الامتدادات المجانية المطلوبة وجدولة ماسح الإشارات كل خمس دقائق. من دون هذه
   الخطوة لن تُنشأ إشارات تلقائياً.
6. شغّل **Build Android APK** من GitHub Actions. افحص
   `https://<project-ref>.supabase.co/functions/v1/api/health` للتأكد من أن
   الواجهة وقاعدة البيانات تستجيبان. سجّل الحساب أولاً من تطبيق المستخدم
   باستخدام البريد المدرج في `ADMIN_EMAILS`، ثم أكّد البريد من الرسالة وسجّل
   الدخول إلى تطبيق المدير بهذا الحساب.

مفتاح `service_role` لا يوضع مطلقاً في التطبيق أو GitHub Variables. يحتفظ به
Supabase كإعداد خادمي تلقائي. لا تشغّل ترحيل SQL على قاعدة تحتوي جداول بهذه
الأسماء مسبقاً من دون مراجعة مخططها أولاً.

## البناء السحابي

يجهّز `.github/workflows/build.yml` Java 17 وFlutter وPython على GitHub Actions،
ويشغّل اختبارات الخادم والتطبيقين، ثم ينتج APK منفصلاً للمستخدمين وAPK للمدير.
كلاهما يستهدف `minSdk = 21` ويملك إذن الإنترنت. اسما التطبيقين **كريبتو
البلحوسي** و**كريبتو البلحوسي - المدير**. يفعّل كلاهما `FLAG_SECURE` لتقليل
لقطات الشاشة/التسجيل المعتادة؛ لا يمنع ذلك التصوير بجهاز خارجي أو نظام مخترق.

نزّل APK المطلوب من **Artifacts** في تشغيل GitHub Actions. البناء غير موقّع
بمفتاح توزيع إنتاجي؛ يلزم إعداد توقيع آمن قبل النشر العام.

## ملاحظات المنتج والسلامة

- درجة الإشارة هي درجة توافق فني من 100، وليست احتمال ربح أو ضماناً.
- يرفض الخادم نشر أي إشارة تقل درجتها عن 65/100.
- يحدد الخادم وحده انتهاء التجربة/الاشتراك؛ وقت الهاتف لا يمنح وصولاً إضافياً.
- يجب عرض مصادر الأخبار وروابطها، لا نسخ المقالات.
- بيانات التحليل عامة للقراءة فقط؛ لا تُستخدم مفاتيح خاصة ولا يُرسل أي أمر تداول.
- حظر لقطات الشاشة المعتادة عبر `FLAG_SECURE` ليس حماية مطلقة من جهاز خارجي أو
  نظام مخترق.
- يتطلب تأكيد البريد إعداد مفتاح Brevo ومرسل موثق في أسرار النشر. وإشعارات
  الدفع في الخلفية عبر FCM لا تُرسل بعد؛ الخدمة تحفظ أحداث الصفقة لكن لا تدّعي
  تسليم Push.
- يجب إعداد قاعدة البيانات وسر JWT والبريد وHTTPS وحساب المدير وتوقيع APK
  بإعداد إنتاجي قبل إتاحة التطبيقين. مراجعة الاستراتيجية واختبارها تاريخياً
  وواجهة TradingView المضمنة ما زالت من أعمال المرحلة التالية.
